3 ОПИС ВИКОНАНОЇ РОБОТИ

Для доповіді обрано мову програмування Kotlin. Kotlin – статично типізована мова від компанії JetBrains. Вона працює на JVM, Android, у браузері та як нативний код і повністю сумісна з Java. З 2019 року Google рекомендує Kotlin як основну мову для Android.

Рекомендації взято з офіційного документа Kotlin Coding Conventions [1] і документації Kotlin [2-4]. Також використано стиль Android [5] і книгу “Clean Code” [6].

Для прикладів написано невелику програму обліку замовлень у книгарні. Програма виводить склад замовлення, рахує суму зі знижкою, проводить оплату і читає кількість з рядка. Зроблено дві версії: OrderProcessingBefore.kt без рекомендацій і OrderProcessingAfter.kt з рекомендаціями. Код обох версій наведено в додатку В. Обидві версії виводять однаковий результат:

Покупець: Олег Шевченко, oleg.shevchenko92@gmail.com
Замовлення (2 позиції):
  1984 (Джордж Орвелл): 2 × 450 грн = 900 грн
  Капітал (Карл Маркс): 1 × 520 грн = 520 грн
До оплати зі знижкою 10%: 1278 грн
Баланс 1500 грн → Оплачено 1278 грн
Баланс 500 грн → Помилка оплати: Недостатньо коштів
Кількість з введення "abc": 1 (це не число, тому взято 1 за замовчуванням)

Перші рядки виводу показують покупця та склад замовлення. Програма рахує суму зі знижкою 10 % (1278 грн) і виконує оплату двічі: при балансі 1500 грн оплата проходить, при балансі 500 грн повертається помилка.

Остання рядок перевіряє обробку некоректного вводу: рядок «abc» не є числом, тому функція toIntOrNull повертає null, а оператор ?: підставляє значення за замовчуванням, 1. Програма при цьому не падає. Версія до змін досягає того самого через try-catch. Однаковий вивід обох версій підтверджує, що рефакторинг не змінив поведінку програми.

Далі описано 7 рекомендацій. Для кожної вказано, що вона означає, де її видно в коді і чому вона важлива. Слайди презентації наведено в додатку Б, відеозапис доповіді – в додатку А.

3.1 Форматування коду

Рекомендація. Оформлювати код однаково, за правилами Kotlin Coding Conventions [1].

Опис. Відступ дорівнює 4 пробілам, табуляція не використовується. Відкривна фігурна дужка стоїть у кінці рядка з оголошенням. Навколо операторів і після коми ставиться пробіл. Якщо параметри не вміщаються в один рядок, кожен пишеться окремо, а після останнього ставиться кома. Android-стиль [5] обмежує довжину рядка 100 символами.

Приклад. У версії до змін клас OrderService має дужки на окремих рядках і відступ 2 пробіли (додаток В.1, рядки 16–25). У версії після змін функцію calculateTotal оформлено за правилами (додаток В.2, рядки 47–50). Довгий виклик println у функції main перенесено на кілька рядків, щоб рядок не перевищував 100 символів (рядки 92–95). У версії до змін є рядки довжиною понад 130 символів (рядок 66). Слайд з цим прикладом показано на рисунку Б.4.

Пояснення. Код з однаковим форматуванням читається швидше. Кома після останнього параметра потрібна, щоб при додаванні нового параметра в Git змінювався лише один рядок. Якщо кожен у команді форматує по-своєму, в комітах з’являються зайві зміни і конфлікти при злитті гілок.

3.2 Іменування

Рекомендація. Давати змістовні імена в стилі, прийнятому в Kotlin [1].

Опис. Класи пишуться в PascalCase (OrderService), функції і змінні – в camelCase (calculateTotal), константи – в UPPER_SNAKE_CASE, пакети – малими літерами (bookstore.after). Файл з кількома оголошеннями називається за змістом у PascalCase. Ім’я функції – це дієслово, ім’я класу – іменник [6].

Приклад. У версії до змін є клас book, функція calc і параметри l, d, s, t (додаток В.1, рядки 3–6, рядки 18–24). Число 30 у перевірці знижки нічого не пояснює. У версії після змін використано імена Book, calculateTotal, discountPercent і константу MAX_DISCOUNT_PERCENT (додаток В.2, рядок 4). Слайд показано на рисунку Б.5.

Пояснення. Добре ім’я замінює коментар. З короткими іменами доводиться читати тіло функції, щоб зрозуміти, що вона робить. Перейменування – це метод рефакторингу Rename Method [7], IntelliJ IDEA виконує його автоматично.

3.3 val і незмінні колекції

Рекомендація. Оголошувати змінні через val, а колекції створювати функціями listOf, setOf, mapOf [1, 2].

Опис. var використовується лише тоді, коли значення справді змінюється. Інтерфейс List у Kotlin доступний лише для читання, тому функція, яка отримала List, не може його змінити. Властивості data class теж оголошуються через val.

Приклад. У версії до змін усі змінні оголошено через var, а список книг заповнюється викликами add (додаток В.1, рядки 55–57). У версії після змін список книг створено одним виразом listOf (додаток В.2, рядки 77–80). Слайд показано на рисунку Б.6.

Пояснення. Значення val задається в одному місці, тому його легко відстежити. Змінну var або змінну колекцію можна змінити з будь-якої частини програми, і такі помилки важко знайти, особливо в багатопотоковому коді.

3.4 Null-безпека

Рекомендація. Використовувати null-безпеку Kotlin і не використовувати оператор !! [3].

Опис. Тип String не може містити null, а тип String? може. Компілятор не дає звернутися до nullable-значення без перевірки. Для цього є оператор безпечного виклику ?., оператор Елвіса ?: і функція let. Оператор !! кидає NullPointerException, якщо значення дорівнює null.

Приклад. У версії до змін функція getContact займає 6 рядків, має змінну var і оператор !! (додаток В.1, рядки 39–43). У версії після змін функція contactOf – це один вираз з оператором ?: (додаток В.2, рядки 66–67). Слайд показано на рисунку Б.7.

Пояснення. У Java NullPointerException – одна з найчастіших помилок під час виконання. Kotlin переносить цю перевірку на етап компіляції, а оператор !! знову повертає ризик падіння програми.

3.5 Функції

Рекомендація. Писати короткі функції, які виконують одну дію, і скорочувати їх засобами мови [1, 2].

Опис. Функцію з одного виразу записують через знак = без фігурних дужок і return. Параметри зі значеннями за замовчуванням замінюють перевантажені функції. Іменовані аргументи пояснюють значення під час виклику. Функції-розширення додають поведінку до наявного типу без окремого класу-утиліти. Рядкові шаблони замінюють склеювання рядків через +.

Приклад. У версії до змін виклик item(books[0], 2) не показує, що означає число 2, а рядки складаються через +, а склад замовлення виводить один довгий рядок (додаток В.1, рядок 59, рядок 67). У версії після змін є функція-розширення toMoney (додаток В.2, рядок 36), іменований аргумент quantity = 2 (рядок 82) параметр discountPercent зі значенням 0 за замовчуванням (рядок 49) і вивід складу замовлення через forEach і рядкові шаблони (рядки 91–96). Слайд показано на рисунку Б.8.

Пояснення. Коротку функцію легше прочитати, протестувати і використати повторно [6]. Якщо аргументи передаються лише за позицією, при зміні порядку параметрів однакового типу компілятор помилку не знайде.

3.6 Класи даних і sealed-класи

Рекомендація. Для класів з даними використовувати data class, а для обмеженого набору варіантів – sealed-класи і вираз when [1, 2].

Опис. Для data class компілятор сам створює equals, hashCode, toString і copy. Sealed-інтерфейс задає закритий набір підтипів. Вираз when для sealed-типу перевіряється компілятором: якщо якийсь варіант не оброблено, код не скомпілюється.

Приклад. У версії до змін book та item – звичайні класи з var-властивостями, а функція pay повертає рядки "OK" або "ERR" (додаток В.1, рядки 28–34). У версії після змін Book, OrderItem і Customer – це data class, результат оплати описує sealed interface PaymentResult (додаток В.2, рядки 31–33), а функція describe обробляє його через when (рядки 71–73). Слайд показано на рисунку Б.9.

Пояснення. Рядок з помилкою в літері компілятор не помітить. Якщо до sealed-ієрархії додати новий варіант, компілятор покаже всі місця, де його треба обробити.

3.7 Обробка помилок і документування

Рекомендація. Перевіряти аргументи через require і check, не повертати коди помилок і документувати публічні функції коментарями KDoc [1, 4].

Опис. Функція require кидає IllegalArgumentException, а check – IllegalStateException з повідомленням. Для перетворень є функції, що повертають null замість винятку, наприклад toIntOrNull. Загальний Exception ловити не треба. KDoc-коментар починається з /** і містить теги @param, @return, @property.

Приклад. У версії до змін функція calc повертає -1 при неправильній знижці (додаток В.1, рядок 24), а функція parse ловить будь-який Exception (рядки 46–50). У версії після змін знижку перевіряє require з повідомленням (додаток В.2, рядки 51–52), рядок перетворює toIntOrNull (рядок 69), а клас Book і функція calculateTotal мають KDoc (рядки 6–12, рядки 40–46). Слайд показано на рисунку Б.10.

Пояснення. Значення -1 може непомітно потрапити в розрахунок суми. Широкий catch ховає справжні помилки. KDoc видно в підказках IntelliJ IDEA, а інструмент Dokka генерує з нього документацію.

3.8 Інструменти перевірки і тестування

У IntelliJ IDEA код форматує команда Reformat Code (Ctrl+Alt+L), стиль Kotlin Coding Conventions вмикається в налаштуваннях Code Style. Інструмент ktlint [8] перевіряє і виправляє форматування з командного рядка або в CI. Статичний аналізатор detekt [9] шукає складні функції, магічні числа, довгі списки параметрів та інші проблеми.

Для тестів у Kotlin використовують бібліотеку kotlin.test або JUnit 5. Наприклад, для функції calculateTotal можна написати тест, який перевіряє, що замовлення на 1420 грн зі знижкою 10 % коштує 1278 грн, а знижка 40 % дає IllegalArgumentException.

 21      init {

 28  data class Customer(val name: String, val email: String?)

 30  /** результат оплати (і причина). */
 31  sealed interface PaymentResult {
 32      data class Success(val amount: Int) : PaymentResult
 33      data class Failure(val reason: String) : PaymentResult
 34  }
 35
 36  fun Int.toMoney(): String = "$this грн"
 37
 38  class OrderService {
 39
 40      /**
 41       * Рахує суму замовлення з урахуванням знижки.
 42       *
 43       * @param items товари.
 44       * @param discountPercent знижка в %, від 0 до [MAX_DISCOUNT_PERCENT].
 45       * @return сума до оплати, грн.
 46       */
 47      fun calculateTotal(
 48          items: List<OrderItem>,
 49          discountPercent: Int = 0,
 50      ): Int {
 51          require(discountPercent in 0..MAX_DISCOUNT_PERCENT) {
 52              "Знижка має бути від 0 до $MAX_DISCOUNT_PERCENT %"
 53          }
 54          val subtotal = items.sumOf { it.cost }
 55          return subtotal * (100 - discountPercent) / 100
 56      }
 57
 58      fun pay(total: Int, balance: Int): PaymentResult =
 59          if (balance >= total) {
 60              PaymentResult.Success(total)
 61          } else {
 62              PaymentResult.Failure("Недостатньо коштів")
 63          }
 64  }

 73      is PaymentResult.Failure -> "Помилка оплати: ${result.reason}"
 74  }
